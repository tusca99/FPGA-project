I found the root cause. The `reach_row` function in both VHDL and Python is **algorithmically incorrect**. It uses a "doubling" approach (shifts by 1, 2, 4, 8...) that allows reachability to "jump over" closed cells.

Example where it fails:
- Open row: `10101` (cells 0, 2, 4 open; cells 1, 3 closed)
- Seed: `00100` (only cell 2 is seeded)

After the current `reach_row`:
- Step 1: reach = `00100` (no change, cells 1,3 are closed)
- Step 2: reach = `00100` | ((`00100` << 2 | `00100` >> 2) & `10101`) = `10101`

**Bug:** Cell 0 and cell 4 are marked reachable even though they're NOT connected to cell 2 (cells 1 and 3 are closed). The shift-by-2 "jumps over" the closed cells without verifying the intermediate path.

This is why the FPGA percolates **more often** than BFS — it invents fake horizontal connections.

**Fix:** Use iterative ±1 neighbor expansion (the correct algorithm). For N=64, this is 64 iterations per row. I'll restructure the frontier to process each row over multiple cycles.

def bfs_with_parents(grid):
    grid_steps = len(grid)
    grid_width = len(grid[0])
    visited = [[False] * grid_width for _ in range(grid_steps)]
    parent = {}
    queue = deque()

        if grid[0][col]:
            visited[0][col] = True
            queue.append((0, col))
            parent[(0, col)] = None
    
    while queue:
        row, col = queue.popleft()
        for dr, dc in ((-1, 0), (1, 0), (0, -1), (0, 1)):

## Bugs Found and Fixed

### 1. `reach_row` "Jump Over" Bug (CRITICAL)
**File:** percolation_bfs_frontier.vhd

**Problem:** The log2 shift-OR approach (shifts by 1, 2, 4, 8...) allowed reachability to **jump over closed cells**. Example: open=`10101`, seed=`00100` → cells 0 and 4 incorrectly marked reachable.

**Fix:** Replaced with iterative ±1 neighbor expansion:
```vhdl
new_reach := current_reach or ((left_shift or right_shift) and current_open);
```
Repeated until convergence (typically 1-5 cycles for N=64).

### 2. Spanning Timing Bug
**File:** percolation_bfs_frontier.vhd

**Problem:** Moving spanning check to `COMPLETE` state (commit `52b880d`) caused `p_spanning` and `Done` to update in the same delta cycle. The core read the old `p_spanning='0'` value.

**Fix:** Restored spanning check to `RUN` state when processing the last row, giving `p_spanning` a full cycle to stabilize before `Done` asserts.

### 3. Extra Row Timing Bug
**File:** percolation_bfs_frontier.vhd

**Problem:** `Busy` was combinatorial (`'0' when state=RUN else '1'`). When the last row transitioned to `COMPLETE`, the core still saw `Busy='0'` and sent an extra row, inflating `occupied_sum`.

**Fix:** Restructured FSM to `IDLE → RUN_READY → RUN_PROCESS → COMPLETE`. `Busy='0'` only in `RUN_READY`, preventing extra rows.

### 4. `occupied_sum` Safeguard
**File:** percolation_core.vhd

**Problem:** When `popcount_valid_reg='1'` and `frontier_done_s='1'` coincided, the last row's popcount might not be added to `run_occupied_v` before `occupied_sum` updated.

**Fix:** Added explicit check:
```vhdl
if popcount_valid_reg = '1' then
    run_occupied_v := run_occupied_v + resize(popcount_reg, 32);
end if;
```

## Algorithmic Insight: Directed vs Undirected Percolation

The FPGA implements **directed percolation** (only downward propagation). The BFS reference implements **standard undirected percolation** (4-neighbor). This is a **design choice**, not a bug:

- **Directed:** Higher critical threshold (~0.65 vs ~0.59 for undirected)
- **Undirected:** Allows paths that go down, left, then back up

The plot shows the FPGA curve is shifted right compared to BFS, which is expected for directed percolation.
